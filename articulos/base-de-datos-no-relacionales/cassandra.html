Bases de Datos Columnares

¿Qué es Apache Cassandra?

Publicado: Abril 2026 • Lectura: 12 min

Introducción a Cassandra

Apache Cassandra es una base de datos NoSQL de tipo columnar, diseñada específicamente para manejar volúmenes masivos de datos distribuidos en múltiples servidores. A diferencia de las bases de datos relacionales que organizan la información en filas y columnas tradicionales, Cassandra almacena los datos por columnas, lo que la hace extremadamente eficiente para consultas que involucran grandes cantidades de información.

Desarrollada originalmente por Facebook y ahora mantenida por la Apache Software Foundation, Cassandra es una de las bases de datos NoSQL más populares del mundo, utilizada por empresas como Netflix, Instagram, Twitter y Spotify.

¿Qué son las Bases de Datos Columnares?

Para entender Cassandra, primero necesitamos entender qué es una base de datos columnar. En lugar de guardar los datos organizados por filas completas (como en SQL), las bases de datos columnares agrupan y almacenan los datos por columnas.

Diferencia clave:

  • Base de datos relacional (por filas): Lee toda la fila aunque solo necesites un dato
  • Base de datos columnar: Lee solo las columnas que necesitás, ignorando el resto

Ejemplo práctico: Imaginate que tenés una tabla con millones de usuarios y querés saber la edad promedio. En una base SQL tradicional, tendrías que leer todas las filas completas (nombre, email, edad, dirección, etc.) solo para calcular el promedio de la columna "edad". En Cassandra, leerías solo esa columna directamente, lo que es muchísimo más rápido.

Arquitectura de Cassandra

Conceptos fundamentales:

1. Keyspace

Es el equivalente a una "base de datos" en SQL. Es el contenedor de nivel más alto donde definís tus tablas (llamadas "column families" en Cassandra). Cuando creás un Keyspace, definís:

  • Estrategia de replicación: Cómo se distribuyen las copias de tus datos
  • Factor de replicación: Cuántas copias de cada dato querés mantener

Ejemplo: Un replication_factor: 3 significa que cada dato se guarda en 3 nodos diferentes. Si uno falla, todavía tenés 2 copias disponibles.

2. Column Family (Tabla)

Similar a las tablas en SQL, pero con una diferencia importante: cada fila puede tener columnas completamente diferentes. No estás obligado a que todas las filas tengan la misma estructura.

3. Filas y Columnas

  • Fila: Identificada por una clave primaria única (Row Key)
  • Columna: Tiene tres componentes: nombre, valor y timestamp (marca de tiempo)

El timestamp es importante porque Cassandra usa "last-write-wins" para resolver conflictos: si dos escrituras modifican el mismo dato, gana la más reciente.

Características Principales de Cassandra

1. Escalabilidad Horizontal

Esta es una de las mayores ventajas de Cassandra. Podés agregar más servidores (nodos) para aumentar la capacidad sin tener que apagar nada. Los datos se redistribuyen automáticamente entre todos los nodos disponibles.

2. Alta Disponibilidad

Gracias a su sistema de replicación, Cassandra no tiene un "punto único de falla". Si un nodo se cae, los demás siguen funcionando normalmente y sirven las réplicas de los datos.

3. Consistencia Eventual

Cassandra implementa el modelo BASE (en lugar de ACID como SQL). Esto significa:

  • Basically Available: El sistema siempre responde
  • Soft state: El estado puede cambiar con el tiempo
  • Eventually consistent: Eventualmente todos los nodos tendrán los mismos datos

Podés configurar diferentes niveles de consistencia según tus necesidades:

  • ONE: La operación se considera exitosa si un solo nodo responde (máxima velocidad, mínima consistencia)
  • QUORUM: Requiere que la mayoría de los nodos respondan (equilibrio entre velocidad y consistencia)
  • ALL: Todos los nodos deben responder (máxima consistencia, menor velocidad)

4. Esquema Flexible

A diferencia de SQL donde tenés que definir todas las columnas por adelantado, en Cassandra podés agregar columnas dinámicamente sin afectar las filas existentes.

5. Compresión Eficiente

Como los datos de una columna suelen ser similares entre sí, Cassandra puede comprimirlos muy eficientemente, ahorrando muchísimo espacio de almacenamiento.

Lenguaje CQL (Cassandra Query Language)

Cassandra usa CQL, que es muy similar a SQL. Si ya conocés SQL, aprender CQL te va a resultar súper fácil.

Operaciones Básicas:

Crear un Keyspace:

CREATE KEYSPACE mi_tienda
WITH replication = {
  'class': 'SimpleStrategy',
  'replication_factor': 3
};

Crear una Tabla:

CREATE TABLE usuarios (
  user_id UUID PRIMARY KEY,
  nombre TEXT,
  email TEXT,
  edad INT,
  ciudad TEXT
);

Insertar Datos:

INSERT INTO usuarios (user_id, nombre, email, edad)
VALUES (uuid(), 'Juan Pérez', 'juan@example.com', 28);

Consultar:

SELECT nombre, email FROM usuarios
WHERE user_id = 123e4567-e89b-12d3-a456-426614174000;

TTL (Time-to-Live):

Una característica super útil: podés definir que un dato se borre automáticamente después de cierto tiempo.

INSERT INTO sesiones (session_id, user_id, token)
VALUES ('abc123', uuid(), 'token_secreto')
USING TTL 86400;  // Se borra después de 24 horas

Ventajas de Cassandra

  • Velocidad brutal para lecturas de columnas específicas: Ideal para análisis de datos donde solo necesitás algunas columnas de millones de filas
  • Tolerancia a fallos: No hay punto único de falla. Siempre está disponible
  • Escalabilidad lineal: Agregar nodos aumenta proporcionalmente el rendimiento
  • Diseño para Big Data: Puede manejar petabytes de datos sin problemas
  • Escrituras muy rápidas: Optimizado para alto volumen de escrituras
  • Distribución geográfica: Podés tener nodos en diferentes países/continentes

Desventajas de Cassandra

  • No soporta JOINs: Si necesitás combinar datos de múltiples tablas, tenés que hacerlo en tu aplicación
  • Modelo de consultas limitado: Las consultas tienen que estar diseñadas alrededor de la clave primaria. No podés hacer consultas arbitrarias como en SQL
  • Curva de aprendizaje: Diseñar un buen modelo de datos en Cassandra requiere pensar diferente que en SQL
  • Consistencia eventual: Si necesitás garantías ACID estrictas, Cassandra puede no ser la mejor opción
  • Uso de recursos: Consume bastante memoria y almacenamiento por la replicación

¿Cuándo usar Cassandra?

Cassandra es ideal para:

  • Análisis de series temporales: Logs de aplicaciones, datos de sensores IoT, métricas de rendimiento
  • Sistemas de mensajería: WhatsApp, Messenger, donde hay millones de mensajes por segundo
  • Catálogos de productos: E-commerce con millones de productos
  • Datos geográficamente distribuidos: Aplicaciones globales que necesitan baja latencia en todo el mundo
  • Alta disponibilidad crítica: Sistemas que no pueden caerse nunca (servicios financieros, telecomunicaciones)
  • Big Data analytics: Procesamiento de enormes volúmenes de datos

¿Cuándo NO usar Cassandra?

  • Transacciones complejas: Si necesitás garantías ACID estrictas, mejor usá PostgreSQL
  • Consultas ad-hoc: Si no sabés de antemano qué consultas vas a hacer
  • Volúmenes pequeños de datos: Para aplicaciones chicas, Cassandra es overkill. Usá MongoDB o PostgreSQL
  • Relaciones complejas: Si tu modelo de datos tiene muchas relaciones entre entidades, considerá bases de datos de grafos como Neo4j

Cassandra vs otras bases de datos

Cassandra vs MongoDB

  • Cassandra: Mejor para escrituras masivas y distribución geográfica
  • MongoDB: Mejor para consultas flexibles y esquemas dinámicos

Cassandra vs SQL (PostgreSQL, MySQL)

  • Cassandra: Escalabilidad horizontal infinita, disponibilidad total
  • SQL: Transacciones ACID, JOINs complejos, integridad referencial

Cassandra vs HBase

  • Cassandra: Arquitectura peer-to-peer (todos los nodos son iguales)
  • HBase: Arquitectura master-slave (depende de Hadoop)

Conclusión

Apache Cassandra es una base de datos NoSQL extremadamente poderosa cuando necesitás manejar volúmenes masivos de datos con alta disponibilidad y escalabilidad horizontal. Su arquitectura sin punto único de falla y su capacidad para distribuir datos geográficamente la hacen ideal para aplicaciones a escala global.

Sin embargo, no es la solución universal. Cassandra brilla en escenarios de Big Data, series temporales y alta disponibilidad, pero para aplicaciones pequeñas o que requieren transacciones complejas, existen mejores alternativas.

La clave está en entender tu caso de uso: si necesitás manejar petabytes de datos distribuidos con tolerancia a fallos total, Cassandra es tu mejor aliada. Si estás construyendo una aplicación tradicional con relaciones complejas, probablemente PostgreSQL o MongoDB sean mejores opciones.
